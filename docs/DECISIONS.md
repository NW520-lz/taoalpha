# 架构决策记录

状态说明：下列决定属于**当前设计**；代码、客户端和 OKX 账户能力的实现及验证状态，须以各自版本化验收记录为准。每项列出当时选择的理由、放弃的做法以及触发复议的条件。规则数值属于用户的私有风险配置，不在公开决策记录中写死。

## ADR-001：本地 TypeScript 后端与同一业务入口

**决定：** 第一版使用受支持的 Node.js LTS、TypeScript、本机进程与 SQLite。Codex、Claude Code 的 MCP 适配器和本机 CLI 调用同一后端业务接口。

**理由：** 用户当前手动启动客户端，本机运行能先验证研究、批准和订单闭环；统一入口避免两个客户端各自实现一套风控。

**未采用：** 首版直接部署 24 小时云服务；每个客户端维护独立状态；让 Agent 自行拼交易所 API 请求。

**代价与复议：** 会话关闭后本地组合监控停止。确有全天候需求时再引入常驻调度器，但必须共享同一账本与执行权。多机部署前重新评估存储一致性。

**M0 实现说明（2026-10-28）：** 使用 Node.js 24 内置的 `node:sqlite` 与原生 TypeScript 类型剥离；运行时 schema 使用 zod，十进制计算使用 decimal.js。M0 CLI 已实现，统一 MCP 业务入口仍待开发。

## ADR-002：研究能力与交易写权限分离

**决定：** 研究角色只访问数据和必要账户摘要；密钥只供受控执行适配器使用，后端不暴露绕过风控的原始 OKX 写入工具。

**理由：** 外部内容、工具结果和模型推断不构成资金操作授权。能力分离使研究错误难以直接变成订单。

**未采用：** 用提示词、Skills 说明或 MCP 工具隐藏单独当作资金保护；让研究 Agent 持有完整 API Key 并自觉遵守规则。

**代价与复议：** 需要明确的会话和凭证边界；同一操作系统身份下的恶意进程仍可能读取本机凭据，不能声称实现系统级隔离。

## ADR-003：独立研究、反方质询、主控综合

**决定：** 市场结构、项目事件、量化检验先独立阅读同一版本证据；再由反方审查，最后由主控汇总，并保留异议与缺失项。宿主按真实能力拉取和完成任务。

**理由：** 便于追溯研究路径和发现相互矛盾的假设。宿主 API 能力可能不同，因此必须记录实际并行、串行降级或不可用状态。

**未采用：** 多数票放行；模型自报胜率；假定 MCP 服务天然能启动 Codex / Claude Code 子 Agent；无授权情况下另购模型 API。

**代价与复议：** 多角色带来时间和调用成本，效果要用复盘数据检验。若角色无可验证增益，可缩减角色，但不删除证据与反方审查边界。

## ADR-004：版本化交易卡与可信人工确认

**决定：** 后端生成含入场、止盈止损、预算、风险、证据和异常权限的完整卡片；可信人工入口记录用户对卡片特定版本和哈希的决定。批准与提交分开。

**理由：** 用户批准的是具体可审阅交易，不是聊天中的模糊意图。保护与异常权限在下单前明确，才能在成交后按已授权规则恢复。

**未采用：** 模型调用 `approve` 并自称用户同意；一次授权未来所有交易；先开仓再讨论止损；参数变更沿用旧批准。

**代价与复议：** 需要可靠的真人交互适配器。如果客户端不能可信传递确认，就通过独立本机入口确认；未建立此边界时保持只读。逐卡确认之外的"常设授权 + 否决窗"方式见 ADR-012，它不取消本决定中的卡片版本、哈希绑定和批准与提交分离。

**M1 确认基础（2026-10-29）：** 新增绑定内容哈希与账户范围的不可变确认请求、持久领取/决定和事务内一次性消费。Windows 适配器显示完整内容并通过桌面系统验证；缺少系统验证设备时返回不可用。合成测试和非交互工厂探测不代表真人确认已验收，且该基础尚未联通风险配置或交易执行。具体边界见 [CONFIRMATION_BOUNDARY](CONFIRMATION_BOUNDARY.md)。

## ADR-005：单执行权、持久意图和交易所对账

**决定：** SQLite 保存批准、预留、意图、子动作 ID、风险事件和状态。提交前在本地事务内原子预留，事务提交后才调用交易所。所有客户端共享一个执行者和账本。

**理由：** 解决双客户端竞争、重启恢复、未知提交和重复入场。交易所与本地库没有跨系统事务，对账是必需流程。

**未采用：** 请求超时后直接重试下单；用内存锁作为唯一并发保护；把交易所 HTTP 返回视作最终成交；数据库不可写时无日志下单。

**代价与复议：** 本机单写入者限制水平扩展；以后多机部署须设计分布式执行权和强一致存储，不可简单复制 SQLite 文件。

**M1 局部实现（2026-10-28）：** 已增加内部累计亏损账本：基准、已确认资金事件、净值观察和触线事件在 SQLite 中持久化并禁止改写；双进程写锁有合成测试。预算预留、可信人工恢复、执行意图及 OKX demo 对账尚未实现，不能把账本当前输出当作下单许可。

## ADR-006：借助 OKX 官方工具，产品语义由本项目核验

**决定：** 行情和订单适配器优先复用 OKX Agent Trade Kit / Agent Skills 已核实的能力；本项目负责站点、demo/live、现货与 USDT 永续、合约面值、精度、成本及账户模式的实际校验。

**理由：** 避免重写交易所签名及基础请求；官方工具并不自动完成本项目的风控和批准语义。

**未采用：** 将原始官方下单工具直接暴露给研究 Agent；把“文档说支持”当作当前账户和产品已经通过能力测试。

**代价与复议：** 上游版本和地区支持可能变化。接入时固定版本、审查许可证与接口，按真实 demo 结果调整适配器；不支持的能力阻断对应交易。

**M0 修订（2026-10-28）：** M0 只读取无需签名的 OKX v5 公共 REST，由 `src/okx/public-client.ts` 直接发 GET，并限定 `/api/v5/public/`、`/api/v5/market/` 下的路径。账户、模拟与订单等需签名的接口仍计划优先复用官方工具，接入时须核验具体版本、许可和账户能力。

**M1 读取接入（2026-10-28）：** 已固定 `@okx_ai/okx-trade-mcp@1.5.0`（MIT），通过内部 stdio 连接读取 demo 账户与在途/保护订单；实际能力与工具清单必须再次核验。官方通用 CLI/core runner 不是本项目的只读权限边界。连接器不会向研究入口暴露原始 MCP 调用；真实账户、资金对账和模拟执行仍待验收。配置与依赖边界见 [OKX_DEMO_SETUP](OKX_DEMO_SETUP.md)。

**M1 字段归一（2026-10-28）：** 增加后端内存内的账户配置、权益及 SWAP 数量归一；`totalEq` 按官方含义保留 USD，币种权益与合约张数分别标注，不生成未经核对的 USDT 净值。端点与读取观察时效在固定边界校验，交易所最后更新时间另存，不假称多接口原子快照。CLI 仅公开固定校验状态，不公开归一值；查询通过仍固定阻断新增风险。资金流水、归属、产品和保护核对完成后，才可另接账本与提交前重检。

**M1 账户会话（2026-10-29）：** demo 只读刷新后可持久绑定范围、站点与账户身份摘要，重复身份不能登记为另一个预算范围；身份改变形成持久冲突。跨会话的最新刷新状态用于使旧内存快照失效，重启必须刷新。此机制不确认资金归属、不形成用户批准，也不授予执行权。详见 [ACCOUNT_SESSION](ACCOUNT_SESSION.md)。

## ADR-007：历史验证、模拟闭环、人工准入依次完成

**决定：** 策略和检验门槛先版本化，纳入费用及滑点、样本外检验；随后在真实 OKX 模拟环境跑通批准、下单、成交、保护、异常和恢复；最后由用户独立决定是否启用实盘。

**理由：** 研究想法、历史结果、模拟执行质量和实盘授权是不同证据。尤其短周期合约策略必须计算真实交易成本和执行限制。

**未采用：** 只看模型分析就实盘；本地假订单当作交易所模拟验收；模拟完成自动赋予实盘权限。

**代价与复议：** 准备时间较长；任何验证缺项都保持实盘关闭。盈利不被保证，表现随市场变化需持续复盘。

## ADR-008：手动运行与交易所原生保护

**决定：** 首版由用户手动运行，关闭前展示未成交订单、仓位和交易所确认的保护。不能依赖客户端离线后仍执行本地定时退出或组合止损。

**理由：** 用户当前工作方式是手动开启 Codex / Claude Code。运行边界必须与实际进程生命周期一致。

**未采用：** 把普通交易所止损宣传为全天候组合亏损熔断；没有常驻服务却承诺离线时间退出。

**代价与复议：** 组合阈值在离线期间可能延迟发现。需要更强实时性时，再开发并验证常驻监控及故障告警。

## ADR-009：三种思想贯穿机会发现、检验与复盘

**决定（2026-10-28 修订）：** 《德道经》《实践论》《矛盾论》参与机会选择、机制假设、条件转换、验证与复盘。综合阶段的方法记录是整个过程的汇总，不能将其实现成报告末尾的几句提醒；默认不另设有裁决权的哲学 Agent。

- 《矛盾论》启发研究者明确具体过程，分别记录主要冲突、当前主导方面、机制假设、竞争解释与转变条件。这些字段不互相替代，模型票数也不能证明因果关系。
- 《实践论》启发候选策略把观点写成可证伪条件，预登记规则和评价门槛，经过历史/样本外检查与模拟闭环，并以成交对账和净成本复盘；错误结果保留，新判断另建版本。
- 《德道经》启发按机会条件选择参与、承认未知、等待或放弃，并通过对照评价删减无效指标和角色；对条件转变的关注不能直接变成反转交易规则。

**位置：** 方法版本约束独立研究的提问、综合阶段的证据记录、策略检验设计和事后复盘；交易卡仍经原有确定性风控与人工批准。具体字段和开发顺序见[交易研究与学习闭环规格](STRATEGY_RESEARCH_SPEC.md)，原文版本见[来源研究](research/decision-method-sources.md)。

**理由：** 这些文本可以帮助规范提出问题和复核判断的方式；市场方向、策略效能和订单状态仍须分别由带来源的市场数据、统计验证与交易所对账回答。

**未采用：** 把古籍语句转成未经检验的买卖信号；把“主要矛盾”伪装成模型置信度；用哲学解释绕开确定性风控、策略准入或逐单人工批准。

**代价与复议：** 结构化字段可能产生主观标注偏差，需通过候选可追溯率、反证记录质量、样本外结果及复盘一致性评价。公开文档需区分原文、版本说明和现代产品化推演，不宣称版本学或学术定论。

## ADR-010：以可检验的净收益优势组织研究

**决定：** 研究以明确收益机制、扣费后结果及相近风险条件下的基准比较为目标。建议先研究“有现货成交支持的相对强势延续”，保持候选状态；流动性、窗口、入场退出和检验门槛由独立实验预登记，不把本次文档沉淀视为策略验证或实盘授权。

**理由：** 单次快照、上涨叙事和更多 Agent 都不能证明存在优势。数据时间对齐、成本、可成交性及对照实验能使这一判断接受检验，也能判断复杂研究流程是否值得保留。

**未采用：** 因用了杠杆就要求行情更快兑现；把持仓量/资金费率单独当方向证明；放弃做多后自动做空；短线失败后临时改成长持；只展示效果最好的参数或角色组合。

**代价与复议：** 首版要补充历史时序和实验记录。净收益、回撤、错误减少与模型调用成本分开评价；证据不足时继续研究，失败时记录并淘汰/修订，不能放宽原有风险和授权规则来追求通过。

## ADR-011：低频信号与开仓时冻结的移动止损

**用户确认：** 2026-11-01，用户在对话中对“只做低频”和“移动止损以开仓时冻结的回调价距授权”两项回复“同意全部”。

**决定：** 一、策略只在 4 小时线或日线收盘时产生信号，预期每周至多数张交易卡，与逐单人工批准的节奏相符；不做分钟级或高频策略。二、趋势策略的退出由两项保护组成，二者都在交易卡中列明并随卡一次批准：初始止损（入场价 − 初始倍数 × 信号时 ATR）和 OKX 移动止盈止损单 `move_order_stop`，其回调价距 `callbackSpread` 在开仓时冻结为移动倍数 × 信号时 ATR。交易所按规则抬高触发价不视为改动保护参数；改变回调价距、倍数或初始止损仍须生成新卡并重新批准。

**理由：** 逐单批准使高频策略无法执行。趋势策略依赖“让利润奔跑”，若每次抬高止损都要重新批卡则无法操作；把移动规则冻结为交易所托管的单一参数，既保持一次批准覆盖保护（I-05），又在客户端离线时由交易所继续执行（I-21）。研究回放 `breakout-atr-trailing-v2` 用同一公式（只用已完成 K 线的极值）模拟该保护。

**未采用：** 由本地进程定时改价的移动止损（离线即失效，且每次改价都是保护变更）；只设固定止盈（截断趋势收益）；为追求成交频率放宽逐单批准。

**代价与复议：** 交易所移动止损按盘中最高价跟踪，回放按已完成 K 线跟踪，二者触发点会有差异，需在模拟闭环中用实际成交核对。若用户改为不需要逐单批准的执行模式，或交易所不再支持固定价距的移动止损，应复议本决定。2026-11-02 因 ADR-012 复议：否决窗以分钟计，仍只适合低频信号，本决定继续有效。

## ADR-012：常设授权与否决窗

**用户确认：** 2026-11-02（UTC），用户在对话中回复"A要"，同意以"事先签一份授权规则、每笔交易给可否决的时间窗"替代逐卡手动批准；同一回复同意先完成 M1 模拟闭环。用户另表示希望实操后尽快上实盘；本决定不改变 I-02 中实盘须先有通过检验的策略这一前提，取消该前提需要另行明确确认。

**决定：**

1. **常设授权。** 用户经可信人工入口（ADR-004 的确认基础）确认一份冻结内容的授权，内容至少包括：环境（demo 或 live）、账户范围与站点、策略标识和版本、允许的标的与产品、单卡最大计划损失、每日最多卡数、每日亏损上限、最多同时持仓数、风险配置版本、否决窗时长和授权到期时间。授权绑定内容哈希，改任一字段都是新授权、须重新确认。
2. **逐卡否决窗。** 后端为授权范围内的每张完整交易卡生成版本与哈希，**在本机入口成功展示后**才开始否决窗；展示失败或无法确认已展示时不开始计时，该卡不会执行。窗口内用户拒绝即作废该卡；拒绝只减少风险，任何本机入口都可提交，不需要系统验证。
3. **默认批准的来源。** 窗口结束且没有已持久化的拒绝时，后端在同一事务内核对授权有效、未撤销、未过期、卡片完全落在授权范围内、展示与窗口记录存在，并记录批准类型 `standing_authorization_veto_window`、授权哈希、卡片哈希和窗口起止时间。批准由后端依据持久记录计算，模型或请求正文都不能声称"窗口已过"或"用户未拒绝"。
4. **范围外的卡。** 任何字段超出授权（标的、损失、卡数、日亏损、持仓数、策略或风控版本）时，不进入否决窗，改为逐卡确认或直接阻断。
5. **其余约束不变。** 提交前重检（I-04）、单一执行意图（I-06/I-07）、保护随卡一次批准（I-05）、风险事件与硬停止（I-15/I-16）照常适用；窗口结束不跳过任何检查。
6. **撤销。** 用户可随时撤销授权，不需要系统验证；撤销立即阻止新卡和尚未结束的窗口，但不撤除已建立的持仓保护（I-05）。
7. **环境顺序。** 先只用于 demo。用于 live 需要同时满足 I-02 的全部条件（通过检验的策略版本、真实模拟闭环、用户独立启用实盘的记录），并由用户另行确认一份 live 授权。

**理由：** 用户希望交易自动执行、保留拒绝权。把用户的真实确认放在一份有上限、有到期、绑定版本的授权上，逐卡只保留否决，比"不回复即同意"更可控：没有授权就没有默认批准，超出授权的卡不会被静默放行。

**未采用：** 没有事先授权的"沉默即同意"；由模型拟定并生效的授权；展示前就开始计时；无上限或无到期的授权；用常设授权跳过 I-02 的实盘前提。

**代价与复议：** 用户可能错过窗口（睡眠、离开），卡片会按授权执行，实际风险由授权上限和每日亏损上限约束，因此上限必须保守。客户端未运行时不出卡也不执行（ADR-008）。当前本机系统验证设备缺失（见 CONFIRMATION_BOUNDARY），授权尚不能完成真人确认；在此之前保持不可执行。若窗口展示无法可靠确认，或用户要求取消 I-02 前提，应复议本决定。

## ADR-013：50 USDT 实盘执行验证（I-02 的有限例外）

**用户确认：** 2026-11-02（UTC），用户在对话中明确表示："先做完系统收尾（解锁流程、拒绝和撤销的验收），我给你一周的时间测试模拟盘，然后直接上实盘用 50u 测试"。用户此前已被告知：目前没有任何策略通过历史检验，按现有策略的预期收益扣除成本为负。

**决定：** 在 I-02"实盘须有通过检验的策略"之外，允许一次有界的**实盘执行验证**，条件全部满足才可启用：

1. **前置**：模拟盘闭环已完成拒绝、撤销、风险锁人工解锁的真实验收，并在模拟盘连续运行约一周且无未解决的对账阻断。
2. **资金上限**：实盘受管资金不超过 50 USDT；风险配置的现货预算、单卡损失、当日亏损上限按此资金设定，且仅现货、不用杠杆、不做合约。
3. **策略标注**：只能使用标注为验证用途的策略版本（如 `pipeline-test`），卡片与授权明确写明"实盘执行验证，非盈利策略"。
4. **独立确认**：用户经 Windows Hello 单独确认一份实盘启用记录和一份 live 常设授权；demo 授权不能用于实盘。
5. **其余约束不变**：卡片、否决窗、提交前重检、单一意图、交易所托管保护、对账、风险锁与干净币种规则全部照常适用。

**理由：** 用户要在真实市场核对手续费、滑点、成交与保护行为，这些只有真实账户能给出；以 50 USDT 为上限，把最坏结果限定在用户可接受的学习成本内。

**未采用：** 在没有模拟盘验收的情况下直接上实盘；以盈利为目标扩大资金；为未通过检验的策略（趋势 v0/v2、网格 v1）开实盘。

**代价与复议：** 预期为小额亏损（手续费与滑点）。任何增加资金、换用未验证的盈利型策略或取消上述条件，都须新的用户确认并新增决策。出现保护失效、对账不明或连续执行异常时停止并复盘。
