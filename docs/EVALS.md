# 验证与评价方案

当前仓库只有文档，**没有测试代码、基准结果、历史回测或 OKX 模拟订单记录**。下表定义未来实现时的验收方法；只有实际运行并保存证据后才可标记通过。报告必须区分本地替身、真实 OKX demo、实盘三种环境。

## 验证层次与交付门槛

| 阶段 | 必需证据 | 可以宣称 | 不可由此宣称 |
| --- | --- | --- | --- |
| 文档阶段（当前） | 需求、约束、架构与验收案例互相一致 | 可以开始分解实施 | 服务可运行、策略有效或账户已连接 |
| M0 只读研究 | 真实公开行情样本、来源和时间字段、研究角色运行记录、等待/放弃案例、零交易所写请求 | 研究入口可用 | 有可执行策略或已通过模拟 |
| 策略历史验证 | 预先固定规则和门槛、历史数据质量、成本模型、样本外结果、可复算报告 | 该版本策略满足或未满足其预定门槛 | 保证未来盈利 |
| M1 模拟闭环 | 真实 OKX demo 订单、成交与保护 ID；故障和恢复演练；账户与产品能力核验 | 指定站点和产品的模拟执行已验证 | 实盘已开放或执行质量相同 |
| M2 实盘准入 | 前述报告通过、账户基准与配置核实、用户明确启用记录、逐卡批准 | 只可在已授权范围内提交实盘订单 | 无人值守开仓或收益保证 |

## 外部行为测试矩阵

| 用例组 | 对应约束 | 关键断言与可保存证据 |
| --- | --- | --- |
| 行情与研究 | I-01、I-19、I-20 | 公开报价包含产品、站点、交易所/接收时间及单位；数据过期、缺失、注入指令时输出阻断或等待，交易写调用为零；独立角色同证据版本先完成、反方随后运行 |
| 卡片与确认 | I-02–I-05 | 未批准、错账户/环境、过期/改版哈希、伪造用户字段均拒绝；完整止盈止损一次确认；保护修改需新批准；实盘准入不能代替逐单批准 |
| 并发与恢复 | I-06–I-09 | 同卡两客户端并发、重复请求、进程崩溃和超时已受理等场景只有一个意图；稳定子订单 ID 不重复新增敞口；未知状态继续预留并查询 |
| 数量与组合 | I-10–I-13 | spot 基础币数量、合约张数及面值换算可人工复核；取整后风险仍达标；分拆不能绕预算、名额及单笔限制；同币现货与合约 gross/net、成本分别可见 |

| 保护异常 | I-08、I-17、I-18 | 部分成交、撤单时继续成交、止损覆盖不足/未知、止盈单独失败、旧仓位保护仍在；只退出该意图新增敞口，未核对结果仍显示未解决 |
| 故障与离线 | I-07、I-19、I-21、I-22 | 数据库不可写、执行锁冲突、网络失联和站点不支持时禁止新增风险；关闭前显示交易所保护与离线边界；日志无凭证和真实账户资料 |

测试从对外 CLI/MCP 和受控交易所适配器边界进入，不只测试内部函数。故障注入使用记录响应的受控替身，但替身通过不算真实 OKX demo 通过。

## 必测的合成账本例子

用合成初始净值 `500 USDT`、累计净亏损停止门槛 `100 USDT`：若无入出金，净值为 `400` 时触线；若后来实际净入金 `50`，净值为 `450` 时触线。路径 `500 → 620 → 530` 仍为净盈利 `30`，不按最高净值回撤触线。上述例子只检验公式，不代表用户真实资金或项目默认参数。

费用和资金费若已体现在当前净值，不能再次扣减；浮动盈亏仍要算。关键报价缺失、资金流未知或账户资产未覆盖时，结果标为无法核对并阻止新增风险。用属性测试覆盖金额精度、取整边界、不同成交顺序和重复事件输入。

## 策略研究与基准

每个策略版本在查看验证区结果前固定：适用币种与产品、数据时间窗、入场/失效/退出规则、费用、滑点、资金费假设、样本外切分方式和通过门槛。原始数据来源、缺失区间、时间戳与币种幸存偏差需记录。不能让 Agent 看完结果后无版本变更地选择最好阈值。

研究报告至少展示候选数、可交易候选数、数据覆盖、交易次数、净收益与成本、最大回撤、策略在不同时间段与标的上的表现，以及与事先指定基准的比较。胜率和收益分布必须来自实际交易或可复算回测；样本不足时写明不足。模型分歧、弃做建议、错误和调用成本同样计入评价。任何策略门槛未达成时记录失败，不把哲学纪律或 Agent 票数替代统计证据。

## 工程指标与结果格式

- **安全计数：** 未经批准的交易所写请求数、同卡重复新增风险数、超限仍执行数、保护失败却继续增险数，目标均为 **0**。分母和测试覆盖随报告附上。
- **对账覆盖：** 每个已提交意图都有卡片、批准、客户订单 ID、交易所订单/成交引用及最终状态或明确未解决项；不能把 `unknown` 计作成功。
- **研究可追溯率：** 每项交易候选能定位证据版本、实际参与角色、策略版本和反方意见；缺失项需单列。
- **恢复时长：** 从重启到识别待核对意图、从网络恢复到取得确定订单状态，分别测量分位数；先建立基线，再依据真实网络与产品能力确定目标，不在文档阶段伪造 SLA。
- **风险检查开销：** 在本地可复现样本上测量规则计算及 SQLite 预留耗时，与交易所网络等待分开；并发时不能为追求延迟牺牲唯一意图约束。

每份测试记录至少保存：代码提交、策略/风控版本、运行时间、环境与站点、产品、测试步骤、原始响应或脱敏引用、预期、实际结果、未覆盖项目。只有通过真实 OKX demo 的现货与永续完整闭环，才能将 M1 对应能力标为已验证；M2 还需独立准入与逐单确认。
