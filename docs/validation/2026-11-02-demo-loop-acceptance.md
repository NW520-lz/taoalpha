# OKX demo 闭环验收（第一部分，2026-11-02）

证据类型：**真实 OKX global 模拟账户上的下单闭环**，经 `npm run demo:run`。策略为"管道验证"（`pipeline-test` v1，非交易策略），只验证出卡、否决窗、下单、保护与对账链路，不构成任何策略验证或实盘准入。记录只含状态，不含金额、账户标识或交易所订单号。

## 已验证

| 步骤 | 结果 |
| --- | --- |
| 风险配置与常设授权（ADR-012） | 用户本人经 Windows Hello 确认，两项分别为 confirmed / active（第一次真人确认） |
| 本机否决窗 | 窗口显示内容的哈希与卡片一致后才开始计时；用户未操作，窗口结束后后端核对授权与限额并记录批准 |
| 执行意图 | 批准被消费为唯一意图，入场、初始止损、移动止损的客户订单号固定 |
| 提交前重检与入场 | 重检通过后先记录再发送；BTC-USDT 市价买单（按基础币数量）被受理并成交 |
| 保护 | 按实际持有量（扣除以 BTC 计的手续费、按最小数量取整）挂出初始止损条件单与冻结回调价距的移动止损单，均被受理 |
| 对账 | 成交后对账无阻断；`status` 显示入场 filled、初始止损 live、移动止损 live |
| 限额 | 持仓期间再运行一轮，编卡即被风控拦下（`entry.spot_budget`、`entry.spot_plan_loss`），未进入否决窗、未下单 |

## 真实异常处置（同日）

用户为卖出账户中非受管的 BTC，在 OKX 页面手动撤销了该意图的两张保护单。之后的 `status` 对账报告 `reconcile.protection_missing`（入场已成交、初始止损不在挂、条件单历史中无触发记录）并阻止新增风险；账户中另有一张用户挂的 OKB-USDT 限价卖单，判为 `reconcile.unmanaged_order`，系统未触碰。随后按卡片已批准的异常处置执行：记录风险锁（`protection_missing_user_cancelled`），以市价卖出该意图自身持有量（成交量扣除以 BTC 计的手续费、按最小数量取整），按客户订单号确认成交后将意图记为已退出。风险锁仍在，目前没有解锁入口（I-15 解锁流程未实现），因此新的入场会被提交前重检拒绝。

同日还发现：每个意图的两张保护单彼此独立，一张触发后另一张可能卖出非受管的同币种持仓；已以"授权币种只能有受管持有量"与"触发后撤销另一张"两道措施修复（`b31c9d9`），用户随后卖出了账户里额外的 BTC。

## 解锁与撤销（同日）

- 风险锁人工解锁（I-15）：`demo:run unlock` 对唯一一把锁（`protection_missing_user_cancelled`，其意图已退出）发起恢复，用户经 Windows Hello 确认，结果 unlocked，`status` 不再列出该锁。
- 撤销授权：`demo:run revoke` 不经系统验证即把 v1 授权标为 revoked；随后 `cycle` 返回 `cycle.no_active_grant`，未出卡、未下单。随后用户经 Windows Hello 确认 v2 授权（内容同 v1，仅版本号不同），状态 active。撤销时没有持仓，因此"撤销不撤除已有保护"尚未在真实持仓下验证。
- 发现并修复：`setup` 对已确认的风险配置重新提出会因冻结内容不同被拒绝，改为跳过已确认的版本。

## 验收过程中由真实运行发现并修复的问题

均先补测试再修复，期间没有发出任何订单：

1. 账户快照只有 30 秒有效期，行情与账户读取后读取授权即失败并导致崩溃 → 授权读取失败按"无有效授权"处理，并在提交、显示、结算前刷新会话（`ba1152b`）。
2. 否决窗在自己的数据库事务内读取授权，而真实会话读取快照需要开启事务，嵌套失败使所有卡片显示为"无授权" → 授权在事务外读取，加回归测试（`a676363`）。
3. 本机时钟比 OKX 慢约 4.5 秒，报价时间戳被当作"来自未来"而在提交前重检时判为过期 → 允许最多 10 秒的交易所时钟领先；卡片过期且从未发单的意图释放占用；先打开下单连接再取报价（`2f3704e`）。
4. 否决窗脚本中的中文在 Windows PowerShell 5.1 下乱码 → 脚本只含 ASCII，文字以 UTF-8 数据传入，并以显示内容哈希校验（`661c863`）。
