# 不可破坏的约束

这些规则适用于 CLI、MCP、未来服务进程及交易所适配器。数值预算和门槛由已确认、版本化的用户风险配置提供；仓库不预置个人资金数字。某个外部能力不足时，新增风险操作应被阻断，不能让模型临时放宽规则。

| ID | 必须成立的性质 | 可观察的反例 |
| --- | --- | --- |
| I-01 | 研究与执行权限分离。研究角色不能接触写入凭证或可绕过风控的原始交易所写接口 | 一份研究报告直接调用下单工具 |
| I-02 | 实盘必须具备固定版本的策略规则、含成本及样本外历史验证、真实模拟闭环、用户独立启用记录；每笔仍需单独批准 | 回测缺失或模拟通过后自动开实盘 |
| I-03 | 新增风险只来源于一张完整且有效的交易卡，绑定账户、环境、卡片内容哈希及策略/风控版本，并通过可信人工确认 | 模型输出 `approved: true` 就下单 |
| I-04 | 提交前重检账户、产品能力、行情时效、保护方式、价格、预算及全部风险锁。卡片变更或超界须重新出卡和批准 | 批准后市场变动仍沿旧金额强行成交 |
| I-05 | 交易卡一次批准覆盖其中明确列出的止盈止损和异常处置；改动保护参数须重新批准。入场批准过期不解除既有持仓保护 | 到期清掉交易所止损或擅自放宽止损 |
| I-06 | 同一卡片版本和账户范围只能消费出一个持久执行意图；每个子动作使用唯一稳定的客户订单标识 | 重试、双客户端或重启造成第二个开仓意图 |
| I-07 | 外部副作用与数据库事务无法原子化。先持久化批准消费、预留、意图和子动作，再向交易所写；不明结果先对账 | 网络超时后直接发新开仓请求 |
| I-08 | 订单、成交、保护、意图和风险锁分别记录。发送成功、交易所受理、成交、保护有效、退出完成是不同事实 | HTTP 成功即报告“已安全开仓” |
| I-09 | 结果未知的入场和待成交入场继续占预算、风险与仓位名额；经交易所核对最终状态后才释放 | 平仓请求刚发出就允许新仓 |
| I-10 | 金额、合约张数、基础币数量和报价币价值显式区分，使用十进制定点计算；按交易所精度取整后再次检查约束 | 合约面值换算错误或最小订单使风险超限 |
| I-11 | 单笔计划损失计入预估手续费、资金费和滑点；分批与关联加仓合并计算。计划值不代表最大实际损失 | 拆单绕过单笔上限或把保证金当计划风险 |
| I-12 | 储备、现货、合约分别受已确认预算约束。储备不自动转入亏损仓位；合约逐仓、自动追加关闭、杠杆上限由账户实况核验 | 模式未知时回退全仓或自动补保证金 |
| I-13 | 同币现货和合约可以并存，但分别与合并展示总名义、净方向、成本和计划风险；反向敞口不自动抵扣预算 | 仅展示接近零的净敞口，隐藏两边风险 |
| I-14 | 累计净盈亏 = 当前受管净值 + 已核对出金 − 已核对入金 − 初始受管净值，含浮盈亏且成本只计一次 | 入金当收益或重复扣手续费 |
| I-15 | 提醒、暂停、硬停止及保护异常按各自事件持久化；一次恢复只针对可恢复的具体事件，不解除其他锁，不重置本金基准 | 净值反弹或换策略自动恢复开仓 |
| I-16 | 已确认的产品行为：达到硬停止线后禁止新增风险、撤销增险入场并退出受管合约；现货沿已批准退出计划。执行未核对前不得宣称完成 | 硬停止时无授权清仓现货，或只发平仓请求就解锁 |
| I-17 | 止损未建立、覆盖不足或状态未知时，按卡片授权锁定新增风险、撤销剩余入场并尝试退出该意图新增的敞口；不动无关旧仓位与保护 | 退出操作反向开仓、卖掉旧现货或悄悄继续开仓 |
| I-18 | 只有止盈失败而有效止损仍在时，作为独立异常处理，停止该意图继续增险，不自动套用止损失效的全套退出 | 止盈失败被误判成无止损而平掉旧仓 |
| I-19 | 数据过期、关键来源缺失、账本不可写、锁不可得、账户差异或产品能力不明时不新增风险；失败不能伪装成空行情或零仓位 | API 出错后以空结果继续制卡与下单 |
| I-20 | 策略报告中的事实、推断、来源、时间和真实执行模式分别记录；Agent 投票、哲学文本及模型信心不是盈利证据 | “四个 Agent 同意”被写成 80% 胜率 |
| I-21 | 客户端离线时不承诺本地组合监控或定时退出继续运行；只能说明已被交易所确认接受的保护及其实际边界 | 关闭 Codex 后仍宣称实时执行组合熔断 |
| I-22 | 密钥、Passphrase、访问令牌及真实个人账户资料不进入 Git、模型上下文或可公开日志 | 凭证被写入示例配置或审计正文 |

风控阻断不应屏蔽对已有风险的查询、按批准范围减少敞口或必要的保护恢复。实现需分清“禁止新增风险”和“禁止所有动作”，否则停机规则本身会阻止退出。

每条约束都应能在 [EVALS.md](EVALS.md) 找到行为测试或外部验收证据。规则变化须先记录新的用户确认与版本，在 [DECISIONS.md](DECISIONS.md) 说明原因，再更新测试；不能靠代码默认值静默改动。
